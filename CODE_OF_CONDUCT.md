# Code of conduct

## The short version

Be straight with people and be kind about it. Those are not in tension.

## What this project is about

This is a tool that tells people their code has problems. That makes the tone
of the discussion around it part of the engineering, not separate from it.

Two rules do most of the work here, and they apply to code review and to
conversation equally:

**A confident wrong answer is worse than an incomplete one.** If you do not
know, say so. "I have not measured that" and "I am guessing" are useful
sentences and nobody will think less of you for them. This repository has
deleted two finished features because measurement showed they were wrong, and
corrected its own documentation more than once. That is the normal case, not
an embarrassment.

**Findings are about code, never about the person who wrote it.** A false
positive is a bug in this tool. A real finding is a thing to fix. Neither is a
verdict on anybody's competence, and a report that reads like one is a report
written badly.

## Specifics

Expected:

- Say what you actually think, with the reasoning attached.
- Ask when a requirement is unclear rather than guessing and blaming later.
- Assume the other person had a reason. Ask what it was.
- Accept "no" as an answer, including from a maintainer with less context than
  you. You can disagree and say why; relitigating a settled decision in five
  threads is not disagreement.
- English is a second language for most people here, including the author.
  Read past the grammar to the point.

Not expected:

- Personal attacks, demeaning comments, or making somebody's identity a topic.
- Sexualised language or imagery, and unwelcome attention of any kind.
- Publishing private information without permission.
- Sustained disruption: reopening resolved threads, demanding free work,
  escalating tone to win a technical point.
- Using a finding from this tool to belittle whoever wrote the code. That is
  the specific failure this project would rather not enable.

## Scope

Issues, pull requests, discussions, commit messages, and anywhere someone is
representing the project.

## If something goes wrong

Report it to the maintainer at the address in `pyproject.toml`. Include enough
that it can be understood without asking you to relive it.

What happens next: you get an acknowledgement, the report stays between you
and the maintainer unless you agree otherwise, and you are told what was
decided. Depending on severity that is a private word, a request to edit or
withdraw a comment, a temporary block, or a permanent one.

The maintainer is one person and this is not a company. That means the process
is quick and informal, and it also means the maintainer is not neutral about
their own project. If the problem is with the maintainer, say so plainly —
that is a report worth making, not an awkward one.
